## 2. Frequency-limit service

- [x] 2.1 Add `app/services/ai_rate_limit.py`: `AIRateLimitError(ValueError)` carrying `retry_after_seconds: int`, mirroring `SupportRateLimitError`'s shape in `app/services/support.py`.
- [x] 2.2 Implement `async def enforce_ai_rate_limit(db: AsyncSession, user_id: UUID, *, bucket: str, thresholds: list[tuple[int, int]]) -> None` per design.md Decision 1: for each `(window_seconds, max_count)` in `thresholds`, count `AIRateLimitEvent` rows for `(user_id, bucket)` newer than `now() - window_seconds`. Track the highest `count / max_count` ratio seen across all thresholds and record it via `AI_RATE_LIMIT_USAGE_RATIO.labels(service="core-api", bucket=bucket).observe(ratio)` (design.md Decision 6) — on every call, not just rejections. If that ratio is ≥ 0.8, log `ai.rate_limit.near_limit` (INFO, fields `user_id`, `bucket`, `count`, `limit`, `window_seconds`). On the first exceeded threshold, increment `AI_RATE_LIMIT_REJECTIONS.labels(service="core-api", bucket=bucket)`, log `ai.rate_limit.rejected` (WARNING, same fields), and raise `AIRateLimitError(retry_after_seconds=window_seconds)` (full-window approximation — design.md Risks notes precise computation as a later refinement, not required now). If no threshold is exceeded, insert one `AIRateLimitEvent` row and opportunistically `DELETE` rows for `(user_id, bucket)` older than `max(window_seconds for window_seconds, _ in thresholds)`.
- [x] 2.3 Add `app/config/ai_rate_limits.py` (or equivalent constants module) defining one named threshold list + concurrency limit per bucket from design.md Decision 4's table (`CHAT_MESSAGE_THRESHOLDS`, `CHAT_MESSAGE_CONCURRENCY`, `STORY_REWRITE_THRESHOLDS`, `STORY_REWRITE_CONCURRENCY`, `STORY_CONTEXT_EXTRACT_THRESHOLDS`, `STORY_CONTEXT_EXTRACT_CONCURRENCY`, `STORY_EVOLUTION_THRESHOLDS`, `STORY_EVOLUTION_CONCURRENCY`) — one place to tune after real traffic is observed, per design.md Decision 4.

## 3. Concurrency-guard service

- [x] 3.1 Add `app/services/ai_concurrency.py`: module-level `_active: dict[tuple[UUID, str], int]` guarded by an `asyncio.Lock`; `AIConcurrencyLimitError(ValueError)` carrying `retry_after_seconds: int` (use a short fixed value, e.g. 5s, since concurrency slots free up quickly — not tied to a window like the frequency limiter).
- [x] 3.2 Implement `ai_concurrency_guard(user_id: UUID, *, bucket: str, limit: int)` as an async context manager (`@asynccontextmanager`): under the lock, check `_active.get((user_id, bucket), 0) >= limit` → increment `AI_CONCURRENCY_REJECTIONS.labels(service="core-api", bucket=bucket)`, log `ai.concurrency_limit.rejected` (WARNING, fields `user_id`, `bucket`, `limit`), and raise `AIConcurrencyLimitError`; else increment `_active[(user_id, bucket)]` and `AI_CONCURRENCY_ACTIVE.labels(service="core-api", bucket=bucket).inc()` (design.md Decision 6), `yield`, then decrement both in a `finally` (executes on normal exit, exception, and `GeneratorExit` from caller cancellation) — per design.md Decision 2.
- [x] 3.3 `just validate-backend`.

## 4. Wire into `routes/ai.py`

- [x] 4.1 `send_message` (~ai.py:802-825): immediately after `session = require_auth(request)`, `await enforce_ai_rate_limit(db, session.user_id, bucket="chat_message", thresholds=CHAT_MESSAGE_THRESHOLDS)`, catching `AIRateLimitError` and re-raising as `HTTPException(429, detail=str(e), headers={"Retry-After": str(e.retry_after_seconds)})` — as a pre-stream check, before the `StreamingResponse`/generator is constructed, matching the existing `rewrite_story` pre-stream-check pattern. (Metric/log emission for the rejection happens inside `enforce_ai_rate_limit` itself, task 2.2 — the route only translates the exception to an HTTP response.)
- [x] 4.2 `send_message`: wrap the streaming body with `async with ai_concurrency_guard(session.user_id, bucket="chat_message", limit=CHAT_MESSAGE_CONCURRENCY):` — acquire attempted before entering the `StreamingResponse` generator (so an immediate 429 is possible), guard held for the full generator lifetime; catch `AIConcurrencyLimitError` the same way as 4.1. Implemented via the shared `AIConcurrencySlot.acquire()`/`.release()` helper (added to `ai_concurrency.py` to satisfy design.md's "single shared helper, not four hand-rolled copies" mitigation) rather than a bare `async with`, since the guard must be acquired in the route handler but released from inside the generator's `finally`.
- [x] 4.3 `seed_conversation` (~ai.py:286-299): same two checks as 4.1/4.2, same `chat_message` bucket (design.md Decision 4 groups these two endpoints together). Deviation from the default ordering: the checks are placed as the last step before `seed_stream` is defined (after all early-return paths — the three 204 idempotency short-circuits AND the later 400/500 `HTTPException` paths), not immediately after `require_auth`. This avoids acquiring a concurrency slot that could leak if any later synchronous check raises before the generator (and its `finally: await slot.release()`) exists, and avoids consuming a rate-limit slot on any no-op short-circuit, not just the 204 ones.
- [x] 4.4 `just validate-backend`.
